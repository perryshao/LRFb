## 新确认的 GMM 输出越界

`thirdparty/vlfeat-0.9.20/toolbox/gmm/vl_gmm.c` 定义输出顺序为均值、协方差、
先验、似然、后验，但无条件执行 `OUT(POSTERIORS) = mxCreateNumericMatrix(...)`。
主编码器只请求前三个输出；对只有三个槽位的数组写下标 4，会破坏内存。

第一次直接编译该网关的 Octave 流水线在 GMM 调用后的训练编码阶段发生段错误。
随后独立测试使用精确大小的三槽位输出缓冲区，并对真实网关开启 AddressSanitizer，
复现 **heap-buffer-overflow / WRITE of size 8**，确认输出契约本身有缺陷。
延迟崩溃的位置不等于越界发生的位置。

继续流水线测试时，验证程序生成临时网关：向原实现请求五个输出，返回调用者需要的
前三个，释放其余输出。底层 GMM 公式、训练循环和研究源码没有修改。
这只是隔离缺陷后的验证，原 MEX 源码问题仍需单独修复并重新编译。

## 其他问题与测试适配

1. **圆心单输出越界仍然存在。** 原代码的 ASan 检查再次复现 stack-buffer-overflow；
   Octave 测试网关为它提供三个输出槽位，并检查一、二、三输出调用结果。
   这不表示未经适配的原网关已安全。
2. **MAT 保存格式。** 原 `save -v7.3` 在 Octave 中明确报“不支持”。仅测试路径上的
   `save.m` 改用 v5 MAT 并补 `.mat` 扩展名；调用者变量由其工作区读取。
   已验证此格式下的中间数据和模型读回，未验证 MATLAB v7.3。
3. **小型 IP 数据的空槽位。** 原加载器预分配 8000 列，15 条测试输入留下空槽，
   原 `getLabels` 实际执行出现索引错误。测试在加载器结束后显式裁剪空列再继续。
   原完整数据训练/测试各 8000 条，不受这项小样本适配影响。
4. **旧数值问题由 Octave 再次确认。** 180° 四元数与空池化产生非有限值；
   6 帧序列请求 13 次取样越界；回归正则项解析导数约 2、有限差分约 4。
5. **未消除所有 C++ 风险。** 正常三角形/分段夹具通过原 ASan/UBSan 检查。
   编译仍提示截断的 `orient2dadapt` 缺失返回、MBS 非虚析构函数等历史问题；
   测试不是所有输入下内存安全的证明。
